- Manager page access is governed by public.page_permissions (page_key = route URL) checked in the _authenticated layout guard and sidebar via src/lib/page-permissions.ts; admins bypass. Why: admin assigns per-page access.
- Hand-cash/income-expense totals all come from fetchCashSummary in src/lib/cash-queries.ts; any new money table must be added there. Why: one consistent account across dashboard and reports.
- Staff (daily workers, engine mestri, managers) share the workers table by role; burn mestri (পুড়াই মেস্তুরি) is a sardar with kind='burn'. Earnings come only from src/lib/salary-accrual.ts: daily pay = present days × daily_wage; salary (salaryEarned) accrues inside the selected season from the later of join_date/season start to the earliest of today/leave_date/season end (Dhaka dates); sardarEarned counts kacha_brick_entries production + load + unload (not damage) plus sardar_work_entries, or salary (with pay_rates history) for burn. Earlier seasons' dues live in opening_balances. Why: payments are season-scoped, so earnings must be too.
- Global React Query defaults (staleTime 30s, refetchOnWindowFocus true) and router preload 'intent' live in src/router.tsx; a MutationCache onSuccess there invalidates all queries (and clears the AI cache) after any useMutation succeeds, so writes made outside useMutation must call invalidateQueries themselves. Why: instant page switching.
- AI assistant writes live in saveAiActionToDatabase in src/services/gemini.ts; it runs in the browser only after the user taps "খাতায় সেভ" in chat, and inserts into the same tables the pages use. Why: AI entries must appear everywhere like manual ones.
- Material/parts expenses go to purchases + supplier_payments (not expenses); exception: the cash-book expense form (AddExpenseDialog) saves parts bought without a supplier name to expenses. Why: they must show on the supplier/material page.
- Navigation: sidebar on tablet (md), top dropdown menubar on desktop (lg+), big NavGrid on dashboard for phone/tablet; these three read NAV_GROUPS. Why: one menu source. Exception: the phone bottom bar (src/components/mobile-bottom-nav.tsx, below md) keeps its own short fixed list (home, challans/approvals, AI chat, reports, preferences).
- Supplier dues can be settled with bricks via the RPC settle_supplier_with_bricks (admin only): it creates an approved challan, a matching collection (method "ইট দিয়ে সমন্বয়") and a supplier payment (method "bricks"), linked by sales_entry_id with ON DELETE CASCADE. Why: brick sale and full expense both count while hand cash stays unchanged; deleting the challan undoes all three.
- Purchase catalog (raw_materials): item_group raw|other picks the folder, pricing unit|total|flex sets the entry form, pay_mode credit|cash decides storage: credit -> purchases (+ supplier_payments), cash (e.g. কারেন্ট বিল) -> expenses with category = item name, which the purchases page reads back into its history. Why: bills never stay due and must hit the cash book once.
- Profit/loss on /income-expense is accrual (fetchProfitLoss in src/lib/pl-queries.ts): purchases count at bill value on purchase_date, supplier_payments are cash only and are not counted again; labour is still counted by payments. Supplier dues (fetchSupplierDues) are all-time, not season-scoped. Hand cash still comes only from fetchCashSummary. Why: material bought on credit is a real cost even before it is paid.
- seasons has a CHECK (end_date > start_date) and the seasons form blocks overlapping active seasons. Why: a reversed range makes every sdb query return nothing.
- Production ledger: mills (মিল ১-৪) hold the current sardar and each kacha entry keeps its own mill_id/sardar_id; per-thousand rates live in production_rates (production|load|unload, effective_from) and only pre-fill new entries; an unload is saved by the RPC save_unload as one kacha_brick_entries 'unload' wage line plus production_entries grade rows linked by unload_entry_id (ON DELETE CASCADE). Why: a sardar or rate change must never rewrite past entries, and unload wages, stock and the "পাকা বের" counts all come from one entry.
- Wage/salary history lives in pay_rates (worker_id or sardar_id, amount, effective_from); earnings use rateAt/salaryEarned/dailyEarned in salary-accrual.ts, falling back to workers.daily_wage/monthly_salary or sardars.monthly_salary when a person has no history. Forms that change a wage must write a pay_rates row with the chosen start date. Why: editing a wage must not reprice days already worked.
